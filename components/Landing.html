How does it work?

A repo's Overlens workflow crawls every preview deploy and pushes screenshots to overlens/dev and overlens/pr-{n} branches. This site reads those branches and renders what the PR changed: Split, Onion, 2-up and a pixel-level Difference, at both viewports and in both themes. Buttons marked with data-overlens-press are pressed, and the drawer or dialog each opens is shot too, as its own slide.

The baseline is whichever branch the repo's config names in targetBranch — its snapshots always live in overlens/dev, one commit per crawl. A PR compares against the snapshot of the commit it branched from, so what merged into the target since never shows up as its change. Merging the target in moves it to the latest snapshot.

Installation

Overlens rides on your deploys: every successful GitHub "Preview" or "Production" deployment (Vercel emits these out of the box; other hosts' environment names are one input away) triggers a crawl that screenshots every reachable page and pushes the snapshot branches this site reads. The crawler is an ordinary visitor, so the deploy has to be reachable without a login — Vercel's deployment protection turns every page into the same auth wall.

The crawl engine, the diffing and the PR reporting live in the npm package @ape-egg/overlens, versioned with this inspector and run with bunx from your workflow — it brings its own Playwright (which we have to thank for making all of this possible) and crawls in the matching Playwright container image, so every snapshot rasterises text on one font stack — render a baseline on one runner image and a PR on another and every glyph shifts a subpixel, which reads as every page having changed. Your repo installs nothing. Two files make the integration, and one command writes both:

1 overlens.config.ts — repo root

The only file that's yours to shape: the entry pages, the viewport/theme passes and how your app switches theme. targetBranch decides which branch Overlens compares PRs against — whatever it's called, its snapshots are pushed to overlens/dev. Behind a login, or painting a spinner until a websocket answers? auth and ready are the two hooks for that.

2 .github/workflows/overlens.yml

The trigger, the token's permissions and bunx @ape-egg/overlens@1, which checks out each successful deploy itself, crawls it, diffs the output against the baseline, pushes the snapshot branches, maintains a summary in the source PR's description and cleans up after closed PRs. Pinning @1 takes every release short of a breaking one. Hosts other than Vercel name their environments differently: add ENVIRONMENTS, a regex that matches them, next to GH_TOKEN.

That's it — the next preview deploy on a PR creates overlens/pr-{n}, inspectable right here at overlens.korte.kim/{owner}/{repo}/pull/{n}. One timing note: a deploy that finishes before its PR is opened can't be matched to it and is skipped — the next push after opening the PR picks it up.

Land it on targetBranch first. Until that branch has deployed once there is no overlens/dev to compare against, so a PR opened before then honestly reports every page as new — that first run is the baseline being born, not a regression.

Pressed states — data-overlens-press

A drawer, menu or dialog only exists after a click, so a plain crawl never sees it. Mark the element that opens it with a bare data-overlens-press and every pass presses it once the page itself is shot, waits for running animations to finish and the page to settle, then shoots <page>~<name>.png. Marks inside the opened state are pressed next, as <page>~<name>~<nested>.png. Each state is its own page in the report and its own slide here.

The attribute counts bare, empty or "true" — what React renders for a bare JSX data-overlens-press. Any other value, "false" included, isn't a press. The crawl never looks at what opened: the state is named after the pressed element's own aria-label, else its text — the example above shoots <page>~edit.png and <page>~edit~delete.png. When two presses on a page share a name, the later one gets its place among the page's presses appended, <page>~<name>-<n>.png.

Marked elements with the same tag-and-class ancestry are a group — the rows of a list. Only the first of a group is pressed and shot, so ten rows opening a drawer titled with their own record give one snapshot, named after the first row. Siblings that share ancestry but open different things, like tabs or a toolbar of plain buttons, are one group too: give each a class of its own when every one should be shot. States are per page — the same drawer reached from several pages is shot under each of them. No element is pressed twice within a page's crawl, so a button still visible behind its own drawer isn't opened again.

Only marks on screen count: not hidden, not inert, not parked off-canvas like a closed drawer. Every state starts from a fresh load and replays its clicks, but anything a press saves outside the page — localStorage, the server — carries into the next state, so only mark presses that open things. Each press is a full page load against timeoutMinutes; the rest of a group is never pressed, so it costs nothing.

Masks — data-overlens-mask

Content that changes on every render — a clock, an avatar, a live counter — would read as a change on every run. Mark it and every screenshot, pressed states included, covers it with a solid box.

The attribute counts bare, empty or "true" — what React renders for a bare JSX data-overlens-mask. Any other value, "false" included, leaves the element unmasked. The config's mask adds CSS selectors on top for markup you can't annotate; it never replaces the attribute. The attribute takes over from data-apply-playwright-mask, which is no longer masked unless your config lists it.

On a private repo, sign in with GitHub up top and install the Overlens app on it. The inspector holds nothing of yours; it reads your snapshot branches with your own token, and without one a private repo is indistinguishable from a repo that has never run the workflow.
