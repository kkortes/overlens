How does it work?

A repo's Overlens workflow crawls every preview deploy and pushes screenshots to overlens/dev and overlens/pr-{n} branches. This site reads those branches — tip against tip — and renders what a merge would mean today: Split, Onion, 2-up and a pixel-level Difference, at both viewports and in both themes.

The baseline is whichever branch the repo's config names in targetBranch — its snapshots always live in overlens/dev, the branch this inspector reads.

Installation

Overlens rides on your preview deploys: every successful GitHub "Preview" deployment (Vercel emits these out of the box) triggers a crawl that screenshots every reachable page and pushes the snapshot branches this site reads. The repo needs Bun and Playwright, which we have to thank for making all of this possible; three files make the integration:

1 overlens.config.ts — repo root

The only file that's yours to shape: the crawl entry point, the viewport/theme passes and how your app switches theme. targetBranch decides which branch Overlens compares PRs against — whatever it's called, its snapshots are pushed to overlens/dev. Behind a login, or painting a spinner until a websocket answers? auth and ready are the two hooks for that.

2 tests/overlens.spec.ts

The generic crawl engine: follows every root-relative link, dedupes screenshots by path shape, freezes the clock and masks volatile content. It only reads the config, so tuning the crawl never means editing this file.

3 .github/workflows/overlens.yml

Runs the crawl when a preview deploy succeeds, diffs the output against the baseline, pushes the snapshot branches and maintains a summary in the source PR's description.

That's it — the next preview deploy on a PR creates overlens/pr-{n}, inspectable right here at overlens.korte.kim/{owner}/{repo}/pull/{n}. One timing note: a deploy that finishes before its PR is opened can't be matched to it and is skipped — the next push after opening the PR picks it up.
