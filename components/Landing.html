How does it work?

A repo's Overlens workflow crawls every preview deploy and pushes screenshots to overlens/dev and overlens/pr-{n} branches. This site reads those branches — tip against tip — and renders what a merge would mean today: Split, Onion, 2-up and a pixel-level Difference, at both viewports and in both themes.

The baseline is whichever branch the repo's config names in targetBranch — its snapshots always live in overlens/dev, the branch this inspector reads.

Installation

Overlens rides on your deploys: every successful GitHub "Preview" or "Production" deployment (Vercel emits these out of the box) triggers a crawl that screenshots every reachable page and pushes the snapshot branches this site reads. The crawler is an ordinary visitor, so the deploy has to be reachable without a login — Vercel's deployment protection turns every page into the same auth wall.

The repo needs Bun and Playwright, which we have to thank for making all of this possible — add @playwright/test to your dev dependencies and keep the workflow's container tag on that same version. The crawl runs inside that image so every snapshot rasterises text on one font stack — render a baseline on one runner image and a PR on another and every glyph shifts a subpixel, which reads as every page having changed. Three files make the integration:

1 overlens.config.ts — repo root

The only file that's yours to shape: the crawl entry point, the viewport/theme passes and how your app switches theme. targetBranch decides which branch Overlens compares PRs against — whatever it's called, its snapshots are pushed to overlens/dev. Behind a login, or painting a spinner until a websocket answers? auth and ready are the two hooks for that.

2 tests/overlens.spec.ts

The generic crawl engine: follows every root-relative link, dedupes screenshots by path shape, waits for each page to stop changing before it shoots, freezes the clock and masks volatile content. It only reads the config, so tuning the crawl never means editing this file.

3 .github/workflows/overlens.yml

Runs the crawl when a preview deploy succeeds, diffs the output against the baseline, pushes the snapshot branches and maintains a summary in the source PR's description.

That's it — the next preview deploy on a PR creates overlens/pr-{n}, inspectable right here at overlens.korte.kim/{owner}/{repo}/pull/{n}. One timing note: a deploy that finishes before its PR is opened can't be matched to it and is skipped — the next push after opening the PR picks it up.

Land it on targetBranch first. Until that branch has deployed once there is no overlens/dev to compare against, so a PR opened before then honestly reports every page as new — that first run is the baseline being born, not a regression.

On a private repo, sign in with GitHub up top and install the Overlens app on it. The inspector holds nothing of yours; it reads your snapshot branches with your own token, and without one a private repo is indistinguishable from a repo that has never run the workflow.
